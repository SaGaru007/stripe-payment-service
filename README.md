# Stripe Payment Service

A Spring Boot service that sits between an application and **Stripe Checkout**. It owns the
payment-provider concerns so the rest of the system never talks to Stripe directly: it creates
checkout sessions, looks up their status, expires abandoned ones, verifies signed webhooks, and
reports the outcome to a downstream processing service.

## Why this exists

Payment integrations rot when provider calls are scattered through business code. This service
isolates them behind a small internal API, so the rest of the application depends on
`POST /payments` instead of on Stripe's request shape, field names, or error codes.

A second goal is reliability. Webhooks are the only trustworthy source of payment truth — a
redirect back to `successUrl` proves nothing, because the user can simply close the tab. Every
outcome is therefore decided from a **signature-verified webhook**, not from the browser.

## Architecture

```
Client ──► PaymentController ──► PaymentServiceImpl ──► *Helper (builds the Stripe request)
                                      │                        │
                                      └──► HttpServiceEngine ◄──┘   (JDK HttpClient)
                                                   │
                                                   ▼
                                          api.stripe.com/v1/checkout/sessions

Stripe ──► StripeWebhookController ──► verify signature ──► ProcessStripeEventAsync
                                                                    │
                                                                    ▼
                                                    downstream processing service
```

Each operation follows the same three steps — `prepareHttpRequest` → `makeHttpCall` →
`processResponse` — split into a `CreatePaymentHelper`, `GetPaymentHelper` and
`ExpirePaymentHelper`. Adding a new Stripe endpoint means adding a helper, not editing the
service.

Checkout sessions are created with Stripe's raw REST API over `java.net.http.HttpClient` rather
than the SDK, which keeps the wire format explicit and the dependency surface small. The official
`stripe-java` library is still used for the one thing it does better than hand-rolled code:
`Webhook.constructEvent`, which validates the `Stripe-Signature` HMAC and parses the event.

## Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/payments` | Create a Stripe Checkout session and return its hosted URL |
| `GET` | `/payments/{id}` | Retrieve a session: status, URL, payment state |
| `POST` | `/payments/{id}/expire` | Expire an open session |
| `POST` | `/v1/stripe/webhook` | Receive Stripe events (signature verified) |

Interactive API docs are generated by `springdoc-openapi` — run the service and open
`/swagger-ui/index.html`.

### Create a payment

```http
POST /payments
Content-Type: application/json

{
  "successUrl": "https://example.com/order/success",
  "cancelUrl": "https://example.com/order/cancelled",
  "lineItems": [
    {
      "currency": "usd",
      "quantity": 1,
      "productName": "Annual plan",
      "unitAmount": 4999
    }
  ]
}
```

```json
{
  "id": "cs_test_a1B2c3...",
  "url": "https://checkout.stripe.com/c/pay/cs_test_a1B2c3...",
  "sessionStatus": "open",
  "paymentStatus": "unpaid"
}
```

Redirect the customer to `url`. Amounts are in the currency's smallest unit, so `4999` is `$49.99`.

## Webhook flow

1. Stripe posts an event with a `Stripe-Signature` header.
2. `StripeWebhookServiceImpl` calls `Webhook.constructEvent(payload, signature, secret)`.
   An invalid or replayed signature is rejected before any business logic runs.
3. The event is handed to `ProcessStripeEventAsync`, so Stripe gets its `2xx` immediately and
   does not retry while work is still in flight.
4. Only terminal events are forwarded downstream as a `NotificationRequest` carrying the
   provider reference (`PAYMENT_SUCCESS` for `checkout.session.completed` and
   `checkout.session.async_payment_succeeded`, `PAYMENT_FAILED` for
   `checkout.session.async_payment_failed`). Everything else is logged and ignored.

## Running locally

```bash
export STRIPE_API_KEY=sk_test_...
export STRIPE_WEBHOOK_SECRET=whsec_...
export PROCESSING_NOTIFICATION_URL=http://localhost:8082/v1/payments/notifications
./mvnw spring-boot:run
```

The service listens on `8080` (override with `PORT`). To exercise webhooks locally, forward them
with the Stripe CLI and use the secret it prints:

```bash
stripe listen --forward-to localhost:8080/v1/stripe/webhook
```

### Configuration

| Variable | Required | Description |
| --- | --- | --- |
| `STRIPE_API_KEY` | yes | Stripe secret key (`sk_test_...` / `sk_live_...`) |
| `STRIPE_WEBHOOK_SECRET` | yes | Endpoint signing secret (`whsec_...`) |
| `PROCESSING_NOTIFICATION_URL` | yes | Where payment outcomes are reported |
| `PORT` | no | HTTP port, defaults to `8080` |

Secrets are read from the environment in the `prod` profile and from
`application-dev.properties` during development. **Never commit real keys** — the checked-in
values are placeholders.

### Docker

```bash
docker build -t stripe-payment-service .
docker run -p 8080:8080 \
  -e STRIPE_API_KEY=sk_test_... \
  -e STRIPE_WEBHOOK_SECRET=whsec_... \
  -e PROCESSING_NOTIFICATION_URL=https://example.com/v1/payments/notifications \
  stripe-payment-service
```

Multi-stage build: Maven + JDK 17 to compile, JRE 17 for the runtime image.

## Error handling

Failures are normalised by `GlobalExceptionHandler` into a single error body with a stable
`ErrorCodeEnum` code, so callers can branch on the code instead of parsing prose. Stripe's own
errors are mapped rather than leaked — for example a non-positive quantity is rejected with
`400` before any outbound call is made.
